# Make Knowledge Cards（知识卡片生成）

## Overview

将一段文章、笔记或本地 Markdown/TXT 文件，提炼成一组"一张卡片只讲一个知识点"的知识卡片。每张卡片包含四个固定字段：标题、核心知识、简明解释、例子或自测问题。目标不是复述原文，而是把长文本变成可记忆、可自测的要点。

## When to Use

- 用户粘贴了大段文章 / 笔记，并说"做成知识卡片""提炼要点卡片""整理成复习卡""总结成学习卡片"。
- 用户给出本地 `.md` 或 `.txt` 文件路径，要求从中提取知识点。
- 用户需要把阅读材料的重点结构化，便于记忆或自测。
- 文章为英文时同样适用，输出英文卡片（语言与源文本保持一致）。

不要在本场景之外强行调用：普通摘要、翻译、改写不归本 Skill 管。

## Input Handling

按以下优先级确定输入来源：

1. **本地文件**：若用户给出以 `.md` 或 `.txt` 结尾的路径，用当前运行时提供的文件读取工具打开其全文，作为源文本。
2. **粘贴文本**：若用户在消息中直接粘贴了文章 / 段落，以其为源文本。
3. **不支持的来源**（见 Unsupported）：遇到 PDF、网页 URL、要求自动抓取，或要求导出到 Anki、要求图形界面时，明确拒绝，并说明替代方式——"请把文字粘贴给我，或给我一个 .md/.txt 文件"。

读取后先通读全文、建立整体理解，再开始抽点；切忌逐句扫描式提取。

## Card Schema（每张卡片的固定结构）

严格使用以下四个字段，顺序不变：

- **标题**：用一个具体短语命名"这一个知识点"，避免笼统词（如"关于 X 的介绍"）。
- **核心知识**：一句话陈述该点的本质事实 / 结论 / 定义。
- **简明解释**：2~4 句；原文信息不足时 1 句也可，宁短不长。大白话说明它是什么、为什么重要、怎么理解。不使用未定义的术语；若必须出现术语，用源文本里的内容在同一句内解释。
- **例子或自测问题（二选一）**：
  - 例子：用源文本里自带的具体示例。
  - 自测问题：一个能检验是否真懂的提问，且问题本身必须能用源文本已陈述的内容回答（不要问源文本未解释的原因）。
  - 优先用源文本自带的例子；若源文本没有合适例子，**写自测问题，不要编造例子**。

## Extraction Rules（硬性约束）

1. **只取真正重要的知识**：抓住"承重"的内容——定义、机制、原理、关键结论、决策、易混淆的区别。剔除客套、重复、纯修饰性举例、与主题无关的边角。
2. **一卡一点**：一个知识点独占一张卡。若一个候选同时覆盖两个不同概念，拆成两张。
3. **去重**：源文本用不同话重复同一意思，只做一张卡。
4. **不编造**：每张卡的每句话都必须能在源文本中找到依据。不推断、不延伸、不补充原文没有的事实。源文本未提供的定义不要自行补上（可改为写"自测问题"或省略该点）。
5. **不凑数**：目标 5~8 张。
   - 源文本只有 3 个真要点 → 只出 3 张，并说明"原文要点较少，已如实输出 N 张"。
   - 源文本超过 8 个要点 → 按重要性保留最关键的 5~8 张。
   - 一句话都提炼不出有效知识（如纯闲聊）→ 直接告知"源文本没有可提炼的知识点"，不要硬凑。
6. **语言一致**：卡片语言与源文本保持一致（中文源 → 中文卡；英文源 → 英文卡）。标题保持简洁。

## Input Shape Notes（常见输入形态的处理）

- **技术 / 说明类长文**：点通常密集且相互关联，按"定义—机制—结论"逐层抽点，注意别把"例子"误当成"知识点"。
- **论述 / 观点类文章**：每个独立论点就是一张卡；把论据留在"简明解释"里，不要单独成卡。
- **清单 / 攻略类文章（如"N 个方法"）**：先去重（含义相近的条目合并），再按重要性保留最关键的 5~8 张；不要因为原文列了 10 条就硬出 10 张。
- **极短或闲聊文本**：若只有 1~2 个真要点，如实输出；若完全没有可提炼的知识，直接说明"无知识点"并建议补充材料。
- **带大量外链 / 推荐阅读或广告的文章**（常见于社群科普、自媒体推文）：只有正文**实际陈述**的信息才算知识点；"延伸阅读""推荐这两篇文章"之类的标题清单，以及文中插入的广告，一律剔除。特别注意——若正文只提出问题而把答案交给了外部链接，该点不构成可提炼的知识：要么省略，要么在卡片里指明"原文未展开"，**绝不代它作答**。

## Workflow

1. 确定并读取源文本（见 Input Handling）。
2. 通读，列出候选知识点，按"重要性"排序。
3. 套用 Card Schema 逐张生成，遵守 Extraction Rules。
4. 生成后自检：是否编造？是否一卡多点？是否重复？数量是否诚实？
5. 以「**卡片 N**」加四个 `- 字段：` 粗体块的形式输出所有卡片；开头用一句话说明本次张数与取舍原因（如"共 6 张，已舍去 2 个次要重复点"）。
6. 若用户希望落盘，询问后写入 `knowledge-cards.md`（或沿用原文件名加 `.cards.md` 后缀）。

## Output Example

源文本示例（节选）：

> HTTP 是无状态协议，每次请求独立；Cookie 由服务器通过 Set-Cookie 下发，浏览器后续请求自动带上，用于维持登录状态。HTTPS 在 HTTP 之下加了 TLS 加密层。

应输出：

**卡片 1**
- 标题：HTTP 是无状态协议
- 核心知识：HTTP 本身不保存前后请求之间的关系，每次请求都是独立的。
- 简明解释：这意味着服务器默认记不住"你上一秒是谁"。要识别同一用户，需要额外机制（如 Cookie）来携带身份。
- 例子或自测问题：自测——为什么刷新页面后有时需要重新登录？什么机制能避免这种情况？

**卡片 2**
- 标题：Cookie 维持登录状态的原理
- 核心知识：服务器用 Set-Cookie 下发标识，浏览器在后续请求中自动回传，从而让无状态的 HTTP 记住用户。
- 简明解释：登录成功后，服务器把一个"凭证"交给浏览器；之后每次请求浏览器都自动带上它，服务器据此认出用户。
- 例子或自测问题：自测——既然 HTTP 本身无状态，为什么你登录后浏览同一网站的其他页面时，服务器还能认出你？

**卡片 3**
- 标题：HTTPS = HTTP + TLS 加密层
- 核心知识：HTTPS 在 HTTP 之下增加 TLS，对传输内容加密，防止被窃听或篡改。
- 简明解释：两者关系类似"普通邮寄"与"加了上锁信封的邮寄"；应用层用法不变，但链路被加密保护。
- 例子或自测问题：自测——HTTP 和 HTTPS 在"无状态"这一点上有区别吗？

（本例仅 3 个真要点，如实输出 3 张，不凑数。）

## Unsupported（明确不支持）

- 网页抓取 / 自动下载 URL 内容
- 读取或解析 PDF
- 导出到 Anki 或任何特定复习软件
- 图形界面 / 可视化卡片排版

遇到以上需求，说明不支持，并给出可行替代（粘贴文本或提供 .md/.txt）。
